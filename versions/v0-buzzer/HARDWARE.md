# V0 hardware — buzzer bring-up rig

Two connections. That is the point: everything that could go wrong is either the
buzzer, the two wires, or the pin.

## Pin map

| Pin | Direction | Role |
|---|---|---|
| D8 | out | **passive buzzer (+)** — `tone()` or bit-banged `buzz()` |
| GND | — | buzzer (−) |
| D13 | out | on-board LED, lit for the duration of each note (no external part) |
| D0/D1 | UART | note log at 9600 baud |

D8 is deliberate: it is the buzzer pin on **every** version of this project
(V1–V5), so V0 runs on an existing board without moving a single wire. Everything
else on the board can stay connected — V0's firmware never touches those pins.

## Wiring

```
 D8  ──────────── buzzer (+)
 GND ──────────── buzzer (−)
```

## If it still sounds wrong — in order

1. **Does the D13 LED step through the scale?** If yes, the sketch is running and
   toggling the pin on schedule; the fault is the buzzer, a wire, or the pin
   itself. If no, the board is not running this firmware (re-flash, check the port).
2. **Passive or active buzzer?** A passive buzzer is a bare piezo/coil: it plays
   whatever frequency you feed it. An **active** buzzer contains its own
   oscillator, ignores the frequency and only clicks or drones at one pitch —
   which sounds exactly like "not as usual". Active modules usually have a taller
   sealed case and a "+" mark.
3. **Polarity.** Most buzzer *modules* (on a small PCB with pins) are polarised:
   swap + and − and you get little or nothing.
4. **Which playback path fails?** Flash `-e nanoatmega328-buzz` (bit-banged
   `buzz()`, the path the Mario themes use) and compare with the default `tone()`
   build. `tone()` uses Timer2 on the AVR; `buzz()` uses `digitalWrite` +
   `delayMicroseconds`. One being clean and the other not points at firmware
   timing, not at the speaker.
5. **Was the board flashed with an emulation build?** `-DVELXIO_EMULATION` moves
   the buzzer to **D11** in every version of this project. On a D8-wired buzzer
   that is silence. Check the banner on the serial monitor: V0 prints
   `buzzer pin: D8` on a hardware build, `D11` on the emulation build.
6. **Compare against the browser.** The [emulation](emulation/README.md) plays the
   same scale from the same firmware — a reference for what "as usual" is.
7. **Suspect the board itself.** A failing ATmega board can present exactly as a
   bad buzzer. **This is not hypothetical: it is what happened on 2026-07-26.**
   The 2019-era Nano produced a single discontinuous tone that no firmware change
   fixed; the same V0 build on a different Nano played the scale perfectly on the
   first try. If the sound is wrong and everything above checks out, swap boards
   before you replace the buzzer or rewire anything.

   That board's CH340 USB bridge died during the same session (every plug-in
   failing to enumerate with `error -71` across two ports, two cables and with the
   board completely bare). Two failures on one board is a strong hint: if a board
   starts behaving oddly *and* gets flaky over USB, stop debugging the circuit.

## Frequencies played

| Step | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| Note | C4 | D4 | E4 | F4 | G4 | A4 | B4 | C5 |
| Hz | 262 | 294 | 330 | 349 | 392 | 440 | 494 | 523 |

Then back down C5 → D4. This band sits comfortably inside the usable range of a
typical 5 V piezo (which peaks nearer 2–4 kHz, so expect it to be *quiet* but
clean); the game's own key notes are much higher (E6 = 1319 Hz … G7 = 3136 Hz), so
if the scale is clean and the game still sounds off, suspect the higher octaves or
note length, not the buzzer.
